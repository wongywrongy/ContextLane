# ContextLanes v4: one container per lane

Written 2026-11-10. Status: **accepted plan, in progress.** [IMPLEMENTATION.md](IMPLEMENTATION.md) records which phases are done. Until phase 5 the code in this repository is still the v3 host runtime ([V3.md](V3.md)); this document says where it is going and why.

## 1. Why

v3 was designed to run on the host: a lane is a git worktree and a tmux session on the machine, confined by bubblewrap. Putting that whole program in one container needed host paths in `.env`, user ids, two Docker security profiles turned off, toolchains baked into our image, and it stopped every agent on update. Those are symptoms of one mismatch: the lane and the control service were in the same box.

Decisions (Kyle, 2026-11-10):

- Docker is the preferred way to run ContextLanes, and it must be standard.
- A small control service, and **one container per lane**.
- A project is a folder first; lanes live inside a project.
- The command is `contextlanes`. No `cl`, no short verbs. The interactive menus are the easy path; typed commands use full words.

## 2. Principles

Every later choice is checked against these.

1. **The control service never touches your code.** It holds state and asks Docker to do things. Anything that needs a project's files runs in a container that has that one folder mounted.
2. **A lane is a container.** Its checkout, terminal, agent and app live in it. The container is the isolation boundary; there is no inner sandbox.
3. **The project describes its own environment**, with a `devcontainer.json` (the Dev Container standard). No file: a default image.
4. **Nothing to configure before it works.** No `.env`, no user ids, no paths typed by hand. One settings file, with defaults, for the few things that are choices (the domain).
5. **One name per thing.** One command name, one word per action, one place for each setting.
6. **Carry over what works.** Projects and lanes, the event log, inbox and answers, the preview router, the read-only web page, the interactive menus, the `--json` and exit-code contract. v4 changes the layer underneath them.

## 3. Architecture

```
host
├─ /opt/stacks/contextlanes/            compose.yaml, data/
│   └─ container: contextlanes          control service
│        API (private network only) · router :4601 (published) · SQLite · web page
│        mounts: ./data, /var/run/docker.sock
│
├─ docker network: contextlanes         control service + every lane
│
├─ container: cl-shuttleworks-01        a lane
│     image: from the project's devcontainer.json, or the default lane image
│     mounts: the lane's checkout, the project's .git, tools (read-only), agent logins
│     inside: tmux → claude / codex, the app's services, the contextlanes command
├─ container: cl-shuttleworks-02        another lane, same project
│
└─ ~/code/ShuttleWorks/                 the project: your folder, untouched
   ~/code/ShuttleWorks.lanes/01-fix…/   lane checkouts (git worktrees), visible on the host
```

### 3.1 Control service

- One container, one image (`contextlanes`), started by `compose.yaml` in the stack folder. It is the v3 daemon with the runtime layer replaced.
- Mounts `./data` (settings, database, sign-ins) and the Docker socket. It mounts none of the user's folders.
- Publishes one port: the preview router (4601), for the reverse proxy's wildcard entry. Unchanged from v3.
- The API listens on the private Docker network so lanes can reach it by name (`http://contextlanes:4600`). It is never published. Tokens remain the only authority; this replaces the v3 rule "loopback only".
- Runs as root inside its container. It needs the Docker socket, which is root-equivalent on the host anyway. It writes only to `./data`.

### 3.2 Projects

- A project is a git repository folder on the host, registered by its absolute path (`contextlanes add` in the folder). Nothing is copied.
- The control service cannot see the folder, so git operations on it (is it a repository, list branches, add or remove a worktree) run in a short-lived **helper container**: the tools image with that folder mounted at the same path, run as the folder's owner. The existing injected `Runner` gets a Docker-backed implementation for project paths; callers do not change.
- The folder's owner (uid and gid) is read once when the project is added and stored. That replaces `PUID`/`PGID`.

### 3.3 Lanes

A lane is created in this order:

1. **Checkout.** A git worktree of the project at `<project folder>.lanes/<NN>-<slug>` (for `~/code/ShuttleWorks`: `~/code/ShuttleWorks.lanes/01-fix-login`), on a new `lane/NN-…` branch or, with `--branch`, an existing one. Made by a helper container. It is a normal folder on the host, so an editor or `git` on the host sees it, and its branches are in the project's own repository with nothing to push or sync.
2. **Environment.** The lane's container is created with the Dev Container CLI (`@devcontainers/cli`, the reference implementation) from the checkout's `.devcontainer/devcontainer.json`, or from a default configuration (our lane image: Debian, git, Node, Python, mise) when the project has none. The CLI handles images, Dockerfiles, features, Compose-based configs, lifecycle commands, and matching the container user to the folder's owner on Linux.
3. **Mounts.** The checkout and the project's `.git` folder at their host paths (a worktree points at the main repository by absolute path, so same-path mounts keep git working on both sides); the tools volume read-only; the agent-login volume.
4. **Network.** Joined to the `contextlanes` network with a stable name. No ports are published.
5. **Terminal and agent.** A tmux session starts inside the container, running Claude Code or Codex (or a shell for a lane with no agent). Hooks point at the control service by its network name, with the lane's token.

**Tools volume.** A project's image will not contain tmux, the agent CLIs or the `contextlanes` command. They are injected: one Docker volume, filled by the control image when it starts, mounted read-only in every lane and put first on `PATH`. It holds a static tmux, a Node runtime with the `contextlanes` CLI, and Claude Code and Codex at the pinned versions. This is how VS Code and Coder put their agents into arbitrary images. It needs a glibc Linux image with git and a shell; Alpine images are out of scope at first.

**Agent logins.** One volume holds the agents' own config and credentials, mounted into each lane, so signing in once covers every lane.

**Git credentials.** None by default. Lanes commit; the branches are already in your repository on the host, and you push from the host. Forwarding an SSH agent or a token into lanes is an explicit setting, off by default.

### 3.4 A lane's app and its links

- The recipe (`.contextlanes.json`) still says how to start the app, what healthy means and which service is `web`. Approval by the owner is unchanged.
- Services are processes inside the lane's container, started with `docker exec` and watched by the control service. This is a third supervisor driver (`docker`) behind the existing `Supervisor` interface, and it must pass the existing contract test.
- Each lane has its own network namespace, so every lane can use the app's real port (3000 in all of them). Port allocation goes away. Services listen on `0.0.0.0` inside the container, which only the private network can reach.
- The router keeps its job and its hostnames; a route's target becomes `cl-shuttleworks-01:3000` instead of `127.0.0.1:<allocated port>`.
- Databases and other side services belong to the project's dev container (Compose-based `devcontainer.json`), which is the standard way to declare them.

### 3.5 Isolation and the rules that change

| v3 rule (AGENTS.md) | v4 |
|---|---|
| Lane commands run in the bubblewrap sandbox | Lane commands run in the lane's container. bubblewrap and `[sandbox]` are removed |
| The sandbox can be off, never silently | No off switch: a lane always has a container |
| Loopback only, credentials always | Private network only, never published, credentials always |
| Host-specific commands go through a driver | Unchanged; the driver is `docker` |
| Agents never approve; the web app views and decides | Unchanged |

- A lane can read its own checkout, the project's `.git`, the tools, the agent logins and its own lane token. It cannot see `./data`, other projects, other lanes' checkouts or the host.
- The Docker socket is never given to a lane. A project that needs Docker inside its dev container says so in its own `devcontainer.json`, which is the owner's explicit choice; `doctor` flags it.
- The control service holding the socket is the trust anchor, as with Portainer or Dockge.

### 3.6 Lifecycle

- **Updating ContextLanes** replaces only the control container. Lanes are separate containers and keep running; the control service finds them again by their labels.
- **Host reboot.** Lane containers restart (`unless-stopped`); a small start script in the tools volume brings tmux back and resumes the agent's session.
- **Deleting a lane** removes its container and worktree. The branch is kept unless it is a `lane/` branch and the owner asks.

## 4. The command

One name: `contextlanes`. In v4 the installer puts one small script on the host that runs the command in the control container and passes the current folder as text (the control service only needs the path, not the files). Opening a lane's terminal attaches straight to the lane's container.

`contextlanes` with nothing after it opens the menus: Projects → a project's lanes → one lane, with a way back at every level. Typed commands use one full word per action; a missing argument is asked for in a terminal and is exit 2 everywhere else.

| Command | Does |
|---|---|
| `contextlanes` | The menus |
| `contextlanes add [folder]` | Make a folder a project |
| `contextlanes projects` | List projects |
| `contextlanes remove <project>` | Stop tracking one |
| `contextlanes new "<task>"` | Start a lane in this project (`--branch`, `--base`, `--agent`, `--no-agent`, `--here`) |
| `contextlanes claude [args…]`, `contextlanes codex [args…]` | Start that agent in a new lane and attach |
| `contextlanes list` | Open lanes and what they wait on (`--all`: deleted ones too) |
| `contextlanes status [lane]` | The machine, or one lane |
| `contextlanes open <lane>` | Attach to the lane's terminal |
| `contextlanes send <lane> "<text>"` | Message its agent |
| `contextlanes rename <lane> "<task>"` | Rename it |
| `contextlanes resume <lane>` | Start the lane's agent again where it left off |
| `contextlanes auto <lane> on\|off` | Let ContextLanes allow safe requests once for you |
| `contextlanes delete <lane>` | Stop and delete it (`--force`, `--delete-branch`) |
| `contextlanes app start\|stop\|restart\|status [lane] [service…]` | The lane's app |
| `contextlanes logs <service> [lane]`, `contextlanes url [service] [lane]` | Its logs and link |
| `contextlanes recipe [lane]`, `contextlanes approve [lane]` | Read and approve a recipe |
| `contextlanes inbox`, `contextlanes answer <id> <option>` | What waits on you |
| `contextlanes doctor`, `contextlanes setup` | The machine |

Removed: `cl`, and every second spelling (`lane start`, `lanes`, `ls`, `up`, `down`, `ps`, `say`, `sh`, `rm`, `ok`, `env …`, `term`, `lane rm`, `lane rename`, `lane restart`, `lane auto`, `recipe approve`). A lane is still its number inside a project (`2`) or `project/number` anywhere. Agents inside a lane use the same words (`contextlanes app start`), and the agent notes match.

## 5. Install and settings (v4)

```sh
git clone https://github.com/wongywrongy/ContextLane.git /opt/stacks/contextlanes
cd /opt/stacks/contextlanes
docker compose up -d
./install-command          # puts `contextlanes` on PATH
contextlanes               # in any repository
```

- `compose.yaml` has no variables to fill in. No `.env`.
- Settings are one file, `data/config.toml`, created with defaults on first start: the domain for links from other devices, the default lane image, resource limits per lane, whether to forward git credentials.
- A published image (GHCR) replaces the local build once CI publishes one; until then `docker compose up -d --build`.

## 6. What is removed, and when

Removed in phase 0 (it is not the architecture):

- The single-container stack: `Dockerfile`, `compose.yaml`, `.env.example`, `docker/`, `docs/DOCKER.md`, and the `CONTEXTLANES_DOCKER` and `CONTEXTLANES_UNMOUNTED` branches in the daemon and CLI.
- `cl` and the short verbs.

Removed in phase 5, once v4 does everything v3 did:

- The host install: `install.sh`, `install.ts`, `update.ts`, the systemd and process supervisors.
- bubblewrap: `sandbox.ts`, `[sandbox]`, `confineGit`'s sandbox prefix (git on project folders already runs in helper containers).
- Features that only exist as systemd units: ACP lane hosts (`apps/lanehost`), schedules, adoption. The other frozen features (review, architecture, insights, helper) stay behind their flags and are not ported in this plan.

## 7. Phases

Images cannot be pulled or run where the code is written, so each phase is unit-tested with a fake runner and then **run on a real machine with one script whose output is pasted back**. Phases are sized so a failure there points at one thing.

| # | Phase | Delivers | Checked on the machine by |
|---|---|---|---|
| 0 | Clear the ground | Remove the single-container stack and `cl`; one command vocabulary; this document; AGENTS.md rules updated | `pnpm check` only |
| 1 | **Spike, no product code** | One throwaway script (`scripts/v4-spike/v4-spike.sh`) that proves the three unknowns on a real project: the Dev Container CLI run from a helper container against the host's Docker; the tools volume (static tmux, Node, Claude Code, Codex) working in an image that has none of them; files written in the lane owned by the folder's owner | Run the script on a repository; attach to tmux; reach a port from a second container |
| 2 | Control service | `compose.yaml` with no variables; API on the private network; Docker-backed runner and helper containers; `add`, `projects`, branches working with no folders mounted; the host command | `contextlanes add` in a repository, `contextlanes projects`, `contextlanes doctor` |
| 3 | Lanes | `docker` supervisor driver passing the contract test; lane create and delete (worktree + container); terminal attach; agent launch, hooks and inbox; lanes found again after the control service restarts | `contextlanes new`, `open`, an agent asking permission and being answered, restart the stack with a lane running |
| 4 | Apps and links | Services inside the lane; router targets by container name; recipe ports; logs and health; `doctor` checks for Docker and the network | `contextlanes app start`, open the link through the proxy, hot reload |
| 5 | Finish | Resume after reboot; update without stopping lanes; limits and credential settings; web terminal (watch-only) through the lane container; delete the host-only code; README and docs | Reboot with a lane running; update the stack with a lane running |

Phase 1 is the go/no-go. If the Dev Container CLI cannot be driven this way, the fallback is to implement the subset we need ourselves (image or Dockerfile, mounts, environment, lifecycle commands) and state plainly which parts of `devcontainer.json` are honoured.

## 8. Risks

| Risk | Why it matters | Handling |
|---|---|---|
| Dev Container CLI driven from a container | It reads the project folder and talks to Docker; both must line up through same-path mounts. The flags expected (`--override-config`, `--id-label`, `--mount`, `--remote-env`) were not confirmed from documentation | Phase 1 proves it, starting with `devcontainer up --help` |
| Tools volume in arbitrary images | Static tmux and the agent CLIs must run on whatever glibc image a project uses | Phase 1; glibc-only stated up front |
| Agent logins shared by a volume | Claude Code has open reports of its config-directory variable misbehaving in containers | Phase 1 signs in once and starts a second lane to confirm |
| Docker socket | Root-equivalent on the host | Only the control service has it; stated in README and `doctor` |
| Helper container per git call | Each call costs a container start (a few hundred ms) | Acceptable for add, branches, worktree; batch where it shows |
| Same-path mounts on Docker Desktop (macOS) | File sharing and ownership differ from Linux | Linux first; macOS stated as untested |
| Size | This replaces the runtime layer: `runtime.ts`, the supervisors, terminals, agent launch, install and update | Phases; v3 stays usable on the host until phase 5 |

## 8a. Corrections found while writing the spike

Reading the Dev Container CLI (0.90.0) and writing `scripts/v4-spike/v4-spike.sh` showed where sections 3.1 to 3.6 were wrong or too thin. The spike tests each; phases 2 to 5 follow these, not the text above, where they differ.

| Section | Correction |
|---|---|
| 3.1, 3.3 | The CLI matches the lane's user to **the user the CLI itself runs as**. A root helper maps nothing. The control service must run the CLI as the folder's owner (with the Docker socket's group and a passwd entry for that uid), or files in the checkout end up owned by the image's user. |
| 3.3 mounts | The default workspace mount is `/workspaces/<name>`. A worktree needs its host path, so the lane's config sets `workspaceMount` and `workspaceFolder`. For a project with its own `devcontainer.json`, the control service reads it, adds those keys and the mounts, and passes the result as the override config; a Compose-based config ignores `workspaceMount` and needs its own handling. |
| 3.3 tools volume | `devcontainer up --mount` has no read-only option. The read-only mount goes in the config's `mounts`. |
| 3.2 lane folder | A helper that mounts only the project cannot create `<project>.lanes` beside it. Either Docker creates the folder as a mount point and a root helper hands it to the owner, or the parent folder is mounted for that one call. The spike reports which works. |
| 3.3 agent logins | A new volume is owned by root and must be given to the lane's user. Lanes that run as different users cannot share one login volume as it is. |
| 3.4 | `remoteEnv` applies only to commands the CLI runs. A plain `docker exec` from the control service gets the image's `PATH`, so it passes `PATH` or absolute tool paths itself. |
| 3.5 | On Linux a process on the host can usually reach a container's address on the bridge network. "Not published" is not "unreachable from the host", and lanes on the shared network can reach each other. Tokens are the boundary, as before. |
| 3.6 | The CLI builds images named `vsc-<folder>-<hash>-uid` and can write a lock file into the checkout. The control service passes `--no-lockfile` and removes a lane's image with the lane. |

## 8b. Spike result (neo, 2026-11-11)

Run on Ubuntu 24.04, Docker 29.9.3, overlayfs, cgroup v2, against a repository with 89 branches and no `devcontainer.json`. Checks 1 to 8 passed on the first run (about 100 seconds); check 9 (agent sign-in shared by the volume) is manual and still open. **Go.**

| Question | Answer |
|---|---|
| Dev Container CLI driven from a container | Works, as root and as the folder's owner (uid 1000 with the socket's group). `workspaceMount` at the host path, the read-only tools mount in the config, `--no-lockfile` all behave as section 8a says |
| git from a helper with only the project mounted | Works as the folder's owner; `safe.directory` not needed; the worktree's `.git` file points at the host path and host git reads it |
| `<project>.lanes` | Docker creates it as a mount point and a root helper hands it to the owner. The parent folder is never mounted |
| Tools volume | 844 MB. Static tmux 3.6a, Node 24, Claude Code and Codex run in `devcontainers/base:bookworm` and in `debian:bookworm-slim`; read-only in the lane |
| File ownership | Files written in the lane are owned by the folder's owner. **Not proven for an owner other than uid 1000**: the image's own user is 1000 too, so the root run matched by coincidence. Phase 2 runs the CLI as the owner regardless, and phase 3's machine check uses a folder owned by another uid |
| Network | Reached by name from a second container; nothing published; the host reaches the bridge address directly, so tokens stay the boundary |
| Restart | Checkout, mounts and network alias survive `docker restart`; the tmux session does not (the start script in section 3.6) |

## 8c. Corrections found in phase 2

Decisions phase 2 needed that sections 3 to 8b do not make. Each is the conservative choice; change it here first if it proves wrong on the machine.

| Section | Decision |
|---|---|
| 3.1 | **The runtime switch.** `[runtime] mode = "host" \| "docker"` in config.toml. Its default is `docker` only when the image sets `CONTEXTLANES_RUNTIME=docker`; that is read in one function (`defaultRuntime` in `config.ts`) and everything else reads `config.runtime.mode`. In docker mode the data folder defaults to the folder of config.toml (`/data`) and the router to `0.0.0.0` inside the container; a value written in config.toml wins. The host runtime is unchanged |
| 3.1 | **Service and container names.** The compose project is `contextlanes`, the service is `control`, the container is `contextlanes` (`container_name`) with the label `contextlanes.control=1`. A different service name means compose never recreates a container left by the older v3 stack (project `contextlanes`, service `contextlanes`); with the fixed container name, `docker compose up` stops on the name clash instead. The host command checks the label before it runs anything |
| 3.1 | **The router is published on 127.0.0.1:4601**, as v3's default bind was. A proxy on another machine needs `"4601:4601"` in compose.yaml, a deliberate edit |
| 3.1 | **The control service finds its own container** with `docker inspect` (its hostname, then the name `contextlanes`) to learn its image id (helpers run the same image), the host path of `./data` (refused as a project) and what is published and mounted (for doctor) |
| 3.2 | **`add` needs the repository's top folder.** A helper mounts only the folder given, so git cannot walk up to a parent `.git`. `add` in a subfolder, a worktree or a submodule is refused with `not_a_repository`, naming the folder to use. Lane-number lookup from a subfolder still works (it is text) |
| 3.2 | **Two helpers per `add`.** First `stat` as root, with the folder and the root filesystem read-only, no network and no capabilities (reading the owner needs no permission on the folder); then `git rev-parse --show-toplevel --absolute-git-dir` as that owner, which must answer the folder and `<folder>/.git`. Every helper: `--rm`, a `contextlanes-helper-<random>` name, label `contextlanes.helper=1`, `--network none`, `--cap-drop ALL`, `no-new-privileges`, read-only root with a tmpfs `/tmp` for git, one `--mount` at the same path. A helper whose command times out is removed by name |
| 3.2 | **Paths refused before any helper:** not absolute or not normal (`..`, `.`, `//`, a trailing `/`), `~` (the container cannot expand it), control characters, `,` and `"` (`--mount` reads CSV), `/`, anything inside `/proc`, `/sys`, `/dev`, `/run`, `/var/run`, `/boot`, `/etc`, and anything inside or above the Docker socket, `/var/lib/docker` or the stack's `./data`. So the ContextLanes stack folder itself cannot be a project. Docker follows a symlink in a bind source on the host, and these checks see only the text: a link to another folder is mounted as that folder. It is still refused unless that folder is a repository's top with its own `.git` (the git check). Only the owner can add a project |
| 3.2 | **The owner is a project event.** Events were lane-only. Migration 16 adds a small `project_event` log (`project.owner`, payload validated by `packages/protocol/src/project-events.ts`) and `owner_uid`/`owner_gid` columns written in the same transaction. A project listed in config.toml before its owner was read gets it on its first git call |
| 3.3 | **Routes that read project files directly** (lane creation, the recipe, environments, skills, the home folder browser and repository scan, GitHub clone) answer 501 `not_yet` in docker mode until their phase moves them into a container. `/api/projects`, branches, remove and doctor work |
| 4 | **The folder a command runs in** is one input: `CONTEXTLANES_CWD`, set by the host command, validated (absolute, normal) by `apps/cli/src/here.ts`; unset, it is the process's own folder. `add <folder>` resolves a relative folder against it |
| 4 | **The host command** passes `-i` always (so pipes reach the command) and `-t` only when stdin and stdout are both terminals (so `--json` and pipes get plain streams); it execs `docker exec`, so the exit code is the command's; it exits 3 when Docker is missing, the container is stopped or missing, or the container named `contextlanes` lacks the control label. It refuses to overwrite a `contextlanes` it did not write (a v3 install) |
| 5 | **The tools volume** is filled by the image's entrypoint when `<volume>/.version` differs from `/opt/contextlanes-tools/.version` (`tmux=… node=… claude-code=… codex=… layout=1`), the marker copied last. In phase 2 it holds tmux, Node and the agent CLIs; the `contextlanes` CLI joins it in phase 3, when lanes first use it |
| 5 | **doctor in docker mode** replaces the host checks (git, tmux, python3, agents, systemd, bubblewrap) with: Docker reachable and its version, the control container found, the network, the tools volume at the image's version, the API not published, the router published, no mounts beyond data, socket and tools, a trial helper, and a plain line that the control service holds the root-equivalent socket |
| — | **Not addressed in phase 2:** `contextlanes setup` prints a sign-in link to the API on `localhost:4600`, which is not published in Docker; the web page is reachable only through the router (`lanes.<domain>`) until a later phase settles sign-in. `contextlanes daemon` and `update` are host-runtime commands and are not meant to be run inside the container |

## 8d. Corrections found in phase 3

Decisions phase 3 needed that sections 3 to 8c do not make. Written and unit-tested only: **not yet run on a real Docker host.** Change a row here first if the machine check says otherwise.

| Section | Decision |
|---|---|
| 3.3 names | **One name per lane container:** `cl-<project>-<NN>` (`-2`, `-3`… when taken), which is also its tmux session and its alias on the `contextlanes` network. `devcontainer up --id-label` sets `contextlanes.lane=<id>`, `contextlanes.project=<id>` and `contextlanes.instance=<random>`; the random one means the CLI never reuses a container left by an earlier lane with the same id (numbers restart with a fresh database). `--remove-existing-container` is passed as well |
| 3.3, 8a | **The one helper with the socket** runs the Dev Container CLI: `docker run` of the control image as the folder's owner, `--group-add <gid of /var/run/docker.sock as the control container sees it>`, `HOME=/tmp`, `--cap-drop ALL`, `no-new-privileges`, the socket, the checkout and the project's `.git` mounted, nothing else. It keeps the default network (features are downloaded by the CLI) and a writable root. Its config arrives in an environment variable and is written to its own `/tmp`, never into the checkout. No other helper and no lane gets the socket |
| 3.3, 8a | **A user name for the owner's uid.** The control image has one for uid 1000 (`node`). For another uid the helper gets this image's `/etc/passwd` plus one line, from `./data/helpers/passwd-<uid>`, mounted read-only at `/etc/passwd`. That needs the host path of `./data` from `docker inspect`; without it such a lane is refused (`no_data_path`) |
| 3.3 config | **Which devcontainer.json:** `.devcontainer/devcontainer.json`, then `.devcontainer.json`, looked for by a no-socket, no-network, read-only helper; read by `devcontainer read-configuration` (which knows the format). Configs in `.devcontainer/<name>/` are not looked at. Paths in `build` are made absolute against the config's folder (the override file lives elsewhere). Refused before anything is built: Compose (`compose_devcontainer`), and a config that mounts the Docker socket, asks for a privileged container or turns off seccomp or AppArmor (`unsafe_devcontainer`). The default is `[lanes] image` and `[lanes] imageUser` in config.toml (`mcr.microsoft.com/devcontainers/base:bookworm`, `vscode`) |
| 3.3 mounts | The `.git` and agent-login mounts go through `--mount`, the read-only tools mount in the config, as the spike proved. After `up` the control service reads the container's mounts from Docker and removes the lane if it is privileged, has the socket or `./data`, or lacks the checkout, `.git`, the read-only tools or the agent logins |
| 3.3 user | **The lane's user** is the CLI's `remoteUser`; its uid must be the folder's owner's or 0. Any other uid is refused (`lane_user_mismatch`), since the lane would write files that are not the owner's and would take over the owner's login volume. A root lane works and says so (its files belong to root) |
| 3.3 logins | **One agent-login volume per uid**, `contextlanes-agent-home-<uid>`, at `/opt/contextlanes-home`. Each lane's creation runs one root exec that makes `claude/` and `codex/` and gives the top folders (only) to the lane's user. `CLAUDE_CONFIG_DIR` and `CODEX_HOME` point into it, shared by that uid's lanes; v3's per-lane copy of the agent's config is not made. Whether one sign-in carries to a second lane is still unconfirmed (8b) |
| 3.3 lane folder | **The lane's own folder** is `/var/lib/contextlanes-lane` inside the container (0700, the lane user's): the token, the launch file, the task, Claude Code's hooks and MCP files, messages being sent, and unit state. Not the checkout, not a volume: it goes with the container |
| 3.3 token | **The lane token is never an argument.** Host users can read the arguments of container processes in `/proc`. Files go into the lane through `docker exec -i` with the content on stdin (the `Runner` gained `input`). The token is in the launch file and in `/var/lib/contextlanes-lane/token`, which the lane's `contextlanes` reads, so a shell opened before `resume` minted a new token still has the current one. Every lane gets one, including a lane with no agent |
| 3.3 Codex | Codex reads hooks, MCP servers and notes from `CODEX_HOME`, which is now shared: ContextLanes writes the same hook command, MCP entry and `AGENTS.md` notes there for every lane (the lane comes from the environment). Claude Code's are per lane, in the lane folder, through `--settings` and `--mcp-config` |
| 3.3 tools | **The `contextlanes` command in the tools volume** is a single-file ES module bundle (`scripts/lane-tools/bundle.mjs`, esbuild): `cli/cli.mjs`, `cli/toolbox.mjs` (the MCP toolbox), `cli/hook.mjs` and `cli/cli-agent.mjs` (the agent launcher), run by the volume's Node; `bin/contextlanes` is a wrapper. The marker gains `cli=<hash of the bundle>` and `layout=2`, so every release refills the volume |
| 3.3 tmux | tmux in a lane uses its own socket name (`tmux -L contextlanes`), started by a `docker exec` that returns (the server outlives it, as the spike showed), 200×50, mouse on. The agent starts with `respawn-pane` running the launcher on the launch file, as in v3 |
| 3.4 driver | **The docker driver is per lane** (`DockerLanes.supervisor(lane)`): every action is one POSIX sh helper run with `docker exec`, needing only `/proc`, `setsid` and coreutils in the image. A service runs in its own process group under a small loop inside the container that restarts it, so it keeps running while the control container is replaced. A pid counts only with its recorded start time. Listening addresses come from the lane's own `/proc/net/tcp`. `supervisorFor` still answers the process driver in the Docker runtime; nothing starts services in lanes until phase 4 |
| 4 open | **`contextlanes open`** asks the control service for the `docker exec -it -u <user> -w <checkout> -e … cl-… tmux -L contextlanes attach-session` argv (`GET /api/lanes/:project/:n/attach`) and runs it in the control container, where the host command gave it a terminal: host → `docker exec -it contextlanes` → `docker exec -it cl-…` → tmux. Each `docker exec -t` passes the window size and its changes on. It needs a terminal (else exit 2; `--json` prints the command), and it is refused inside a lane (exit 2: lanes have no Docker) |
| 3.6 delete | `delete` removes the container, then its image only when it is named `vsc-…` (never a base image), then the worktree and, when asked and it is a `lane/` branch, the branch. Git in a lane checkout runs in a helper started in `<project>.lanes` with `git -C <checkout>`: Docker would create a missing working folder, and on a bind mount that is a folder on the host. Archive stops the container and keeps the checkout |
| 3.6 found again | **At start** (after the usual recovery) the control service lists containers labelled `contextlanes.lane` and records, for each open lane, `running`, `stopped` or `missing` as a `lane.container` event when it changed; a lane whose container is missing fails with a reason. A lane caught setting up when the control service stopped fails (its last step is unknown). Containers with the label that no open lane owns are reported (log, `doctor`) and never removed. A stopped lane container is not started again: that is phase 5, with the restart policy |
| 3.3 refusals | 501 `not_yet` in the Docker runtime until their phase: a lane's app (`env`, `logs`, `url`, the recipe, environments, skills, and the toolbox's environment tools), review (diff, files, checkpoint, approve, cleanup, fork, hand-off, request changes, and `checkpoint`, `split_lanes`, `get_brief`, `delegate`), taking over changes into a new lane, and `--here`. ACP lanes are refused with `needs_systemd`. The browser's watch-only terminal of a lane container closes with a message (phase 5) |
| 3.6 update | `docker compose up -d` (also with `--build` or `--force-recreate`) replaces only the control container. `docker compose down` would try to remove the `contextlanes` network, which running lanes still use; do not use it while lanes run |

## 9. Decisions taken

1. **Lane checkouts** go beside the project, in `<project folder>.lanes/`: visible, no setting, and never inside the repository where linters and watchers would crawl them.
2. **The host install is dropped** in phase 5, leaving Docker as the only way to run ContextLanes.
3. **The systemd-only features** (ACP lane hosts, schedules, adoption) are dropped in phase 5, not ported.
4. **The command words** are the ones in section 4.
5. **The v3 stack is merged to `main`** before phase 2, so v4 continues from one branch.
