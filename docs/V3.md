# ContextLanes v3: a lane runtime

v3 changes what ContextLanes is for. Real use on 2026-11-01 showed no gain over a plain Claude Code session, and preview links could not be opened from another device. v3 makes two things work well and freezes the rest.

**A lane** is a git worktree, a tmux session, a running copy of the app on its own ports, and a stable link for each service. **Agents** (Claude Code, Codex) run as their own CLIs and use the lane through the `contextlanes` command. **The web app** shows what is happening and takes the two decisions only the owner can make: answering a question or permission, and approving a recipe. **ContextLanes installs as one more service** on a machine that already has a reverse proxy.

**The web app is a viewer.** Signed in from a browser you can read everything and make the two owner decisions; the daemon refuses any other change from a browser session (`apps/daemon/src/http/viewer.ts`), and the lane terminal there is watch-only. Starting, messaging, renaming, restarting and deleting lanes, starting and stopping a lane's app, adding and removing projects and turning Auto on are `contextlanes` commands, which the owner runs on the machine and agents run inside their lane. Settings live in `config.toml`. A frozen feature that the owner turns on brings its own page actions with it.

## Decisions

| Decision | Why |
|---|---|
| One preview router port serves every lane service and the web app, by hostname. Caddy and Tailscale Services modes are removed; Tailscale Serve stays as an option. | One wildcard entry in the proxy the owner already runs is the whole network setup. Configuring someone else's proxy (Caddy's admin API) broke on ordering and was never run for real. Serve is the only mode that had been verified on a real network. |
| Links are `<service>-<n>-<project>.<domain>`, one DNS label. | A wildcard certificate covers exactly one label. The lane number comes before the project so a long project name is what gets cut, and a cut label ends in a hash. |
| Services get `LANE_URL`, `LANE_HOSTNAME` and the same per service; Vite gets its hostname in `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS`. | Dev servers refuse names they were not told about and need the public URL for HMR, CORS and API base URLs. The link is deterministic, so it is known before the service starts. |
| The CLI is the agent interface: `env`, `logs`, `url`, `recipe`, `lane rm`, all with `--json` and fixed exit codes (0 done, 1 failed, 2 usage, 3 unreachable, 4 waiting on the owner). | Agents use command-line tools well. MCP tools only reached agents wrapped by ContextLanes; a CLI reaches any agent, including one the owner runs by hand. Exit 4 lets an agent tell "broken" from "ask the owner". |
| Inside a lane the CLI uses the lane's token and its tool routes only, through a wrapper in the lane's own data folder. | The sandbox hides the data folder, so the installed `~/.local/bin/contextlanes` (which runs through `<data>/current`) cannot run there. Verified under real bubblewrap. |
| Agents learn the commands from Claude Code's appended system prompt, or Codex's `AGENTS.md` in the lane's own `CODEX_HOME`. | An interactive `contextlanes claude` sends no first prompt, so notes in the prompt never arrived. |
| Native-CLI lanes are the default; shell lanes (`--no-agent`, with `--here` for the current checkout) run no agent. | The ACP lane host was the path that showed no gain, and two agent paths doubled the work. A shell lane is the single-CLI case: your own agent, with managed services and links. |
| Everything outside the core is behind `[features]`, off by default: `acp`, `review`, `architecture`, `insights`, `helper`, `sublanes`, `handoff`, `bench`, `schedules`, `adoption`. | Each worked in isolation but together they hid the core. Frozen, not deleted: code and tests stay, and one setting brings a feature back. |
| Lane services run through a supervisor: systemd user units, or process groups the daemon watches. | macOS and Linux without a systemd user session (containers, some VPS images) are common places to run agents. The process supervisor restarts on failure, caps logs, and re-adopts services across a daemon restart. |
| `[sandbox] mode = "off"` only by explicit setting, recorded on every lane, warned about in status and Settings. | bubblewrap is Linux-only. Turning confinement off silently would hide that agents can read the daemon's sign-in token. |
| `contextlanes doctor` checks the whole path through the owner's proxy with a temporary route and a nonce. | Every earlier preview problem was a misconfigured hop that nothing could name. |

## What is core

Projects; CLI and shell lanes; terminals; recipes, environments and per-lane databases; the preview router; hooks and the event log; inbox and answers; notifications; setup and sign-in; doctor; update and backup; project notes and skills; lane cleanup, archive and delete.

## Support

| Platform | What works |
|---|---|
| Linux with a systemd user session | Everything |
| Linux without systemd, macOS | The core. ACP lanes and scheduled lanes need systemd. On macOS agents start only with `[sandbox] mode = "off"`. Run with `contextlanes daemon`. |
| Windows | Through WSL only |

## Checks only the owner can do

1. A wildcard DNS record for the preview domain, pointing at the machine.
2. One wildcard proxy host in the reverse proxy, with a DNS-challenge certificate and WebSockets on ([PROXY.md](PROXY.md)).
3. `[previews] domain` (and `bind` if the proxy runs in Docker), then `contextlanes doctor`.
4. A lane on a real project, opened from a phone and a laptop, with hot reload.
5. `contextlanes claude`, asking the agent to start the environment and load its own link.
